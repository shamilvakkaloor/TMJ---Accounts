**Engineering issues to address during the build**

1. **Bound the atomic financial operation.** One receipt may touch its counter, header, lines, allocations, dues, credit, wallet ledger, audit and public projections. Firestore permits 20 rule document-access calls across a transaction/batch, with a 10-call limit per individual operation. This is not a limit of 20 writes. The proposed document layout needs a tested bound on lines and allocations. Prove a realistic multiline payment, future credit application, refund and reversal using Emulator rule tests before committing to the final layout. Avoid arbitrary limits without testing actual use cases. A failed feasibility test requires a revised design, not weaker rules. [Firebase rule limits](https://firebase.google.com/docs/firestore/quotas#security_rules)

2. **Prevent duplicate submission, not just duplicate numbers.** Assign a stable operation ID before submitting a payment, refund or transfer, and persist its result atomically. On retry or uncertain network outcome, resolve that ID to the existing result. Counter allocation alone would still permit two separately numbered receipts for one repeated submission. Transactions may retry internally and fail offline; receipts become printable only after confirmed commit. [Firebase transactions](https://firebase.google.com/docs/firestore/manage-data/transactions)

3. **Make assessment uniqueness concrete.** Use deterministic document keys for payer + fund + period and separate keys for one-time campaigns. A report index is not the proposed uniqueness mechanism. Reserve imported public IDs transactionally, advance sequence counters safely and retain an external-key mapping for resumable imports. Fund targets become immutable once financial activity exists; changed targets require a new fund. Historical rate snapshots stay fixed.

4. **Avoid widespread rewrites on identity edits.** Current public member records should reference current public house records where practical. Historical receipt snapshots remain immutable. Do not copy changing addresses/Sub Mahal names into every historic due or receipt. Specify transaction boundaries for each small edit and resumable processing for bulk jobs. Public financial projections need a reconciliation check against authoritative events.

5. **Treat balances as constrained calculations.** Reject over-allocation and excessive waivers instead of hiding errors by merely clamping a negative result to zero. Derive payment/waiver states consistently. Distinguish credits received, credits consumed and credits refunded; applying prepaid cash to an assessment creates no second wallet inflow. A reversal must account for credit already applied to a later due. Keep receipt evidence immutable and derive its current void/refund status from linked correction events.

6. **Give large jobs and reports explicit boundaries.** Generation needs a saved period/eligibility snapshot, operation markers, progress and resume handling. A missing-period alert must distinguish no assessments from a partially completed job. Reports need explicit date meanings: cash by payment date, assessments by due period, and balances as of a cutoff. Returns and reversals appear separately from gross receipts. Central and Sub Mahal net collections must use identical filters and attribution rules. Prefer bounded queries or transactional summaries over loading all records on every dashboard visit.

7. **Model quota use before large imports.** Current free Firestore quotas include 50,000 document reads/day, 20,000 writes/day and 1 GiB storage. An illustrative 1,000 houses × 12 monthly periods × two due documents (private/public) already needs 24,000 writes, before audit or job records. A whole-year generation in one day would exceed that write allowance. Smaller resumable runs and measured capacity are necessary. Managed backup/PITR features require billing. [Firestore quotas](https://firebase.google.com/docs/firestore/quotas)

8. **Specify publication and restore behavior.** Public Firestore documents are externally readable under their rules; UI search limits do not make them confidential. Use strict published-field schemas, including receipts and search keys, and deny private collections to unsigned or non-admin users. If fields are later hidden, remove them from existing projections as well. CSV reports are not a complete restorable backup: plan a versioned export of authoritative records, relationships, counters and audit history, with a tested restore into an empty test environment. [Firestore query security](https://firebase.google.com/docs/firestore/security/rules-query)

9. **Complete the release design.** Firebase's generated Hosting GitHub workflow covers Hosting; the project needs explicit Firestore rules/index deployment and appropriate deployment permissions. Test against an emulator or separate test project, since Hosting previews can use the real backend. Deploy compatible rules/indexes before the dependent UI and check index readiness. Record data migrations separately from UI deployment. [Hosting GitHub integration](https://firebase.google.com/docs/hosting/github-integration), [Firebase partial deployment](https://firebase.google.com/docs/cli#deploy_specific_firebase_services)

10. **Keep assets and print scope explicit.** Bundle the initial Mahal logo as a static public asset. Do not assume runtime file uploads or receipt attachments: Cloud Storage is not available under the current Spark offering. Test A6 output with maximum supported lines and long Malayalam names; define continuation pages if one physical A6 page cannot fit the allowed receipt. ID-card physical size is a setup choice. [Firebase pricing](https://firebase.google.com/pricing)

These are implementation responsibilities. They do not require the user to solve Firestore internals.

**Acceptance cases beyond those already in the architecture**

- A member joins or becomes inactive during a period; historical regeneration follows the accepted effective dates.
- A repeated payment submit, two browser tabs or a lost network response creates only one operation result.
- An unrelated authenticated UID cannot read admin records or write any business data.
- A malformed request attempts to change a wallet without its linked financial event, omit the public update, change payer/amount after posting, overpay a due, over-waive it or replay a refund; the rules reject the prohibited state.
- Next-year price is unknown or lower than prepaid credit; money remains traceable without duplicate income or a hidden negative balance.
- A receipt is reversed after its advance has been applied; future dues and wallet effects reconcile. A partial refund followed by correction cannot refund the same money twice.
- A house changes Sub Mahal, followed by a backdated receipt; historical attribution is correct and existing receipts do not change.
- A year-end payment has a posting timestamp in a different year/timezone; receipt sequence, payment date and assessment period remain distinct.
- A generation/import is interrupted and resumed; completed rows are not replayed and the job is not falsely marked complete.
- A historical receipt predates cutover; it appears in the statement without increasing opening cash again. Any remaining refundable historical credit has an explicit opening record.
- Public balance equals the authoritative balance after payment, waiver, credit application, refund and reversal.
- A complete export restores into a clean test environment with matching record counts, IDs, wallet totals, dues and credits.
